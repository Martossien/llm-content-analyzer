# Doc-IA analyzer 3.2.0 — plafond par fichier, comptage exact, alimentation adaptative, extraction recouverte

**Guide de l'utilisateur illustré** : [docs/GUIDE_UTILISATEUR.md](https://github.com/Martossien/llm-content-analyzer/blob/main/docs/GUIDE_UTILISATEUR.md) · [référence des réglages](https://github.com/Martossien/llm-content-analyzer/blob/main/docs/REGLAGES.md) · [journal des changements](https://github.com/Martossien/llm-content-analyzer/blob/main/CHANGELOG.md).

## Installation (poste Windows)
1. Télécharger `docia-3.2.0-windows-x64.zip` ci-dessous, **clic droit → Propriétés → Débloquer**, dézipper.
2. Placer à côté de `Docia.exe` le scanner [`SMBeagle.exe` **4.3.0**](https://github.com/Martossien/smbeagle_enriched/releases/tag/v4.3.0).
3. `Docia.exe doctor` vérifie le poste (DocFuse 0.2.2, pdfium, **OCR Tesseract embarqué** — rien d'autre à installer).

Une campagne 3.0.0 ou 3.1.0 s'ouvre telle quelle : le schéma de base (v7) ne change pas. Le **prompt embarqué change** (en-tête partagé des segments, fichiers seulement cités) : au prochain `run`, les fichiers déjà analysés sont réanalysés avec le nouveau prompt — comportement voulu, voir `docia prompt`.

## Ce qui change pour l'utilisateur
- **Un fichier ne prend plus tout le contexte** : `blocks.max_file_share` (0,3 du contexte servi, « Part du contexte par fichier » dans l'onglet Serveur) ≈ 73 K tokens sur 262 K. Au-dessus, le fichier est découpé — mais seulement si le **serveur** le confirme : docia lui demande le compte exact (`/tokenize`) avant de découper. Un fichier estimé trop long mais qui tient part entier ; un fichier trop long est découpé en segments calibrés sur le rapport estimation/réel mesuré, plus sur un forfait. Mesuré sur 3 documents réels : tous les segments sous le plafond, aucune seconde passe.
- **Les segments savent de quoi ils sont la suite** : chaque partie ≥ 2 s'ouvre sur le début du document (≈ 1 500 caractères, balisé « pour contexte »). Un segment pris au milieu d'un contrat n'est plus sous-classé faute de titre, de parties ou d'objet.
- **Alimentation adaptative** (`llm.adaptive`, case dans l'onglet Serveur, défaut faux) : le run régule les tokens en vol et cherche le meilleur débit du serveur, quel qu'il soit et même s'il change en cours de campagne (autre usage du GPU, préemptions vLLM). Mesuré sur 4×3090 : 181 fichiers, 108 blocs, 0 erreur ; sur cette machine le cache KV n'est pas la limite (25 %), c'est `max_in_flight` — on peut alors le monter à 12–16 et laisser le régulateur trouver la borne. Le budget trouvé est mémorisé par serveur et modèle pour le run suivant.
- **Construction et envoi recouverts** : le lot suivant s'extrait pendant que le lot courant est servi. Sur une grande campagne, plus d'heures de GPU inactif au début.
- **DocFuse 0.2.2** : extraction deux fois plus rapide sur les PDF (pool de processus), sortie identique.
- **Prompt** : un document seulement *cité* dans un texte (pièce jointe nommée, rapport mentionné) n'a plus d'entrée inventée.

## Réglages nouveaux (`docs/REGLAGES.md`)
`blocks.max_file_share` (0.3), `llm.adaptive` (false), `llm.adaptive_start_tokens` (0 = mémorisé, sinon moitié du plafond).
